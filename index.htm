Agentic Systems

01What an agentic system is made of

Strip away the vocabulary and every system on this page is the same nine parts wired differently. A model that holds no memory between calls, a loop that calls it repeatedly, code that decides what goes into each call, tools that let it affect the world, and storage that outlives the conversation. Learn the parts once and the architectures stop looking like competing technologies and start looking like arrangements.

02Workflow, agent, and the space between

The single most consequential design decision is how much the model gets to decide. It is a dial rather than a switch, and turning it up costs determinism, latency, tokens and testability in exchange for the ability to handle situations you did not anticipate.

PropertyWorkflowAgent
Who decides the sequenceYou, in advance, in codeThe model, at run time
Same input, same pathYesNot reliably
Cost per runPredictableVaries by an order of magnitude
TestingPer stage, in isolationEnd to end, statistically
Fails byA stage returning bad outputLooping, wrong tool, plausible wrong answer
Right whenThe steps are knowable in advanceThe steps genuinely depend on what is found

The useful question is not which one you are building. It is which parts of this job vary. Encode the parts that do not, and spend agency only on the parts that do. Most production systems are a fixed skeleton with one or two agentic joints.

03The parts, defined

Nine terms used loosely almost everywhere. The definitions matter less than everyone in the room using the same ones.

Two worked examples

Simple: an expense classifier

  • Shape: a three-step chain, no agency at all
  • Model: small tier throughout, schema-constrained output
  • Context: the receipt, the category list, six examples
  • Tools: one write to the ledger, behind a confidence gate
  • Memory: none needed; each receipt is independent
  • Where the work is: the category enum and the gate threshold

Complex: a support resolution agent

  • Shape: queue, triage classifier, agent loop, approval gate
  • Model: small for triage, large for resolution, both pinned
  • Context: thread, account facts, retrieved policy, trimmed hard
  • Tools: search, account read, draft reply, escalate; send is gated
  • Memory: episodic per customer with expiry, pinned identifiers
  • Where the work is: triage accuracy, retrieval recall, the escalation path

Note what the complex system is: the simple one, plus a queue, plus a gate, plus retrieval. Complexity should arrive as added parts with reasons, not as ambition at the start.

04The build ladder

Climb one rung at a time and stop at the first one that solves the problem. Every rung above your actual need is cost, latency and a new class of failure, bought with nothing in return.

RungWhat it addsClimb when
1. Single callA prompt and a schemaNever skip this; it is your baseline
2. ChainFixed steps, validation betweenOne call is doing three jobs badly
3. RouterClassification then specialised handlersThe prompt has grown branching instructions
4. RetrievalGrounding in your corpusAnswers need material the model cannot know
5. Tool loopModel-chosen sequence, boundedThe steps genuinely depend on what is found
6. Sub-agentsIsolation of context and permissionsOne window cannot hold the work
7. Multi-agentParallel workers and a supervisorMeasured, not assumed, that the above is insufficient

A reliable diagnostic: if you cannot explain why rung five failed at this task, you are not ready for rung six. Teams that skip to the top rung usually end up rebuilding from rung two within a quarter, having learned the same lesson at greater expense.

08Playbooks

Ten repeatable patterns. Each says when the shape applies, the sequence to implement it in, what to measure and how it usually fails. Open one and work down it rather than reading them all. Most real systems are two or three of these composed.

09Runbooks

Ten procedures for the moments when improvising is expensive: a loop that will not stop, a cost spike, a suspected injection, a model being deprecated next month. Written to be followed by someone under time pressure who does not have the context, because that is the situation they are for.

Fifty-one checks across the life of a system, tagged by severity. 15Where does this instruction belong?

The most common configuration mistake is putting everything in the always-on instruction file, which then grows past the point where any of it is reliably followed. The question to ask is not what the instruction says but when it needs to be true, and whether the model is allowed to decline it.

The needPut it inBecause
Applies to every task in this repositoryCLAUDE.md or AGENTS.mdAlways loaded, so keep it short enough to be followed
Applies only to certain files or directoriesA path-scoped ruleCosts nothing when working elsewhere in the codebase
A procedure with steps, run occasionallyA skillMetadata in context, body loaded only when invoked
A side task whose intermediate output is noiseA subagentIts own window, so the main thread stays clean
Must happen every time, without exceptionA hookRuntime code, not a request the model may decline
Must never happenA permission deny rule or sandbox settingEnforced whether the model cooperates or not
Access to an external systemAn MCP serverOne integration, reusable by every client you run
Changes how output is written overallAn output style or verbosity settingApplies to every response rather than one task
Several of the above, shared with a teamA pluginOne installable unit instead of a paste-and-pray README

A useful test: if you would be annoyed to discover the agent had ignored it, it does not belong in an instruction file. Instruction files are guidance. Hooks, permissions and sandbox modes are the only things that hold.

17The hosted surfaces

Repository files are only half of it. The hosted products carry their own configuration, and it is administered by different people with different assumptions, which is where a lot of otherwise sound designs come apart.

What lives outside the repository

  • Connector and MCP approvals decided at the workspace level, not by the developer
  • Which models a plan or tier may use, and what happens when one is retired
  • Project or workspace instructions that apply before any file you wrote
  • Retention: transcripts, prompt history and tool output are plaintext on disk and on the server
  • Confirmation policies requiring approval before consequential actions
  • Admin controls over which sites and desktop applications an agent may touch

GPT-6 Astra, as of this month

  • Announced this week and rolling out across ChatGPT tiers, the API, Azure and Bedrock
  • Positioned around computer use: working through applications that have no API at all
  • Available in ChatGPT Work and Codex, which is where the file-based configuration above applies
  • New enterprise admin controls for approved sites, applications, uploads and browsing history
  • Enterprise plugins in the desktop app, driven by browser use rather than integrations
  • Worth noting: you wrote Astro, the model is Astra; Astro is an unrelated web framework

Computer use as a first-class capability changes the risk calculation in the runbooks rather than adding a new one. An agent that drives applications directly has no tool schema to constrain it and no allowlist boundary by default, so the approval gate stops being a design preference and becomes the only control left.

18A configuration that survives contact

What the above adds up to, for a team that uses more than one tool and does not want to maintain the same conventions in three divergent files.

Do

  • Put the real content in AGENTS.md and keep the per-tool file thin
  • Keep one skill library and symlink it into each tool's path
  • Write permissions, sandbox modes and hooks per tool; they do not abstract
  • Commit what the team shares; keep credentials and personal overrides in the local files
  • Review third-party skills and plugins as untrusted instructions, because that is what they are
  • Re-read the instruction files quarterly and delete what is no longer true

Do not

  • Duplicate conventions across CLAUDE.md and AGENTS.md; they will diverge silently
  • Let the always-on file grow past a couple of hundred lines
  • Encode a hard requirement as an instruction when a hook or permission would enforce it
  • Build an abstraction over two configuration formats that are both still moving
  • Assume a setting you added last quarter is still the one taking effect
  • Forget that transcripts on disk contain whatever your tools printed, including secrets
